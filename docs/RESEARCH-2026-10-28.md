# Article to Note：定位、竞品与开源优化建议

调研日期：2026-10-28。依据本地 v0.2.1 的 README、SKILL.md、scripts、tests，以及下文链接的官方资料和项目仓库。竞品能力来自公开文档，未逐一安装实测；没有取得关键词搜索量、用户规模或转化数据，不据此推断市场份额。本文是建议，不代表维护者已经决定改名或实现路线图。

## 1. 推荐定位

建议主打：**在智能体中读懂网页文章，将可追溯的原文、译文、配图与个人理解沉淀到 Obsidian。**

第一批用户宜聚焦：已经使用 Codex 等本地 Agent、使用 Obsidian、阅读中英文技术文章，并希望保留全文和个人理解的人。这个人群与当前实现匹配，比覆盖所有网页、视频、社交平台的万能剪藏工具更容易验证价值。

抓取适配提供入口，质量检查建立信任，个人理解沉淀形成持续价值。这是产品方向推断，尚需用户验证。单纯“AI 摘要”“Markdown 导出”“支持 Obsidian”已有成熟替代品。

### 当前能力与缺口

| 能力 | 本地证据 | 判断 |
| --- | --- | --- |
| 原文、完整翻译、双语 | SKILL.md；finalize 的 mode/body 参数 | 已有流程；语义完整性依赖宿主审核 |
| 来源与图片清单 | manifest、sourceInventory、verify | 已实现结构与图片检查，不代表自动证明全文完整 |
| 知乎单回答/专栏适配 | zhihu.mjs、browser-capture.mjs、host-browser.md | 有专门适配，真实登录页面尚未完成验证 |
| Obsidian 输出 | 普通 Markdown、相对 assets 路径 | 文件兼容，尚无专用 vault 集成 |
| 选择偏好 | Skill 提问流程、preferences JSON | 已支持；目前主要问输出配置，还没有完整阅读访谈协议 |
| 学习总结与复习题 | Skill 指令允许学习辅助 | 可由宿主生成，尚无专用学习记录模型 |
| 自动关联、去重、更新 | 没有相应 CLI 功能 | 应列为规划 |
| 跨宿主兼容 | 厂商无关的脚本与指令 | 架构意图明确，不能替代逐宿主测试 |

## 2. 竞品与替代方案

选择覆盖一键剪藏、阅读管理、直接 Agent Skill 和提取基础设施的代表项目，不是穷尽列表。

| 项目 | 已核验的公开能力 | 对我们的启发与机会 |
| --- | --- | --- |
| [Obsidian Web Clipper](https://obsidian.md/help/web-clipper) | 免费开源浏览器扩展，保存到本地库，支持高亮、模板；[Interpreter](https://obsidian.md/help/web-clipper/interpreter) 支持自然语言提取、总结、转换和翻译 | 最直接的体验基准。AI 和本地保存不是我们的独有优势；应比较长文翻译质量、失败报告和阅读后的互动 |
| [Readwise / Reader](https://docs.readwise.io/readwise/docs/exporting-highlights/obsidian) | 高亮同步、可定制导出；可导出 Library 内 Reader 文档全文到 Obsidian；追加新高亮以保留用户编辑 | 不能宣称对方只保存摘要。应借鉴阅读与笔记之间的连续流程；当前项目缺乏同步和重复处理 |
| [MarkDownload](https://github.com/deathau/markdownload) | 网页或选中文本转 Markdown、预览编辑与下载，通过 Advanced Obsidian URI 集成 Obsidian | 转 Markdown 已是基础能力；我们需要用可追溯全文、图片验证和交互学习证明额外价值 |
| [kepano/obsidian-skills](https://github.com/kepano/obsidian-skills) | 包含 Obsidian Markdown、CLI、Bases、Canvas、Defuddle 等技能，并面向支持 Skill 的多种 Agent | 最重要的相邻项目和潜在组合对象。不要重做完整 Obsidian 工具箱；专注文章输入与阅读过程 |
| [flyeasy/obsidian-clipper](https://github.com/flyeasy/obsidian-clipper) | OpenClaw Skill；README 声称支持知乎、公众号等，分类、命名与批量保存；知乎使用 direct fetch | 直接同类已经存在。“知乎 + Skill”不够独特；它的真实知乎完整率尚未验证，我们也不能据 README 判定谁更强。其 README 对批量/摘要的当前能力与路线图表述也有重叠，需要实测 |
| [Defuddle](https://github.com/kepano/defuddle) | 浏览器/Node/CLI 正文提取，Markdown、元数据、frontmatter 等输出 | 更适合作为本地通用提取候选；可以减少普通公开页面对 Firecrawl 的依赖，但需独立评估图片和页面兼容性 |
| [Jina Reader](https://github.com/jina-ai/reader) | URL 转面向 LLM 的内容，并提供搜索入口 | 属于上游提取能力，可组合。不要仅围绕 URL 转 Markdown 竞争 |

### 可以主张什么优势

当前代码可以支撑的特点是：宿主负责语言工作、脚本负责可重复的文件操作；保留源文本与成品；记录图片失败并检测遗漏；知乎采用可访问的浏览器页面和专门检查；不把“没有发现截断”表述成全文保证。

这些是具体设计特点，**尚不足以证明优于竞品**。真正的对外优势应来自可复现样例和同条件测试。尤其不要写“唯一支持知乎”“其他工具无法抓知乎”“保证全文”“完全离线”或“适配所有 Harness”。本地浏览器提取不需要 Firecrawl key，但文章仍可能交给远程宿主模型理解或翻译，不能笼统宣传数据绝不离开本机。

## 3. 智能体与 Obsidian 的拓展玩法

优先构建完整的单篇阅读闭环，再扩展多文章任务。

| 场景 | 交互方式 | 建议产物 | 实现状态/顺序 |
| --- | --- | --- | --- |
| 中英技术精读 | 先问阅读目的、熟悉程度；翻译后解释难点 | 原文、译文、术语与用户疑问 | 现有能力可辅助；P1 优化流程 |
| 苏格拉底式阅读 | 每次问一个理解问题，等待回答；追问理由与反例 | 独立学习记录，保留问题、回答、反馈和原文依据 | 最建议新增的 P1 |
| 费曼复述 | 用户先用自己的话解释；Agent 指出缺失和误解 | 初次理解、纠正、最终复述 | 可与访谈模式共用记录结构 |
| 面向项目阅读 | 问“准备用在哪里”；将文章建议转为适用条件与小实验 | 应用笔记、验证清单、未决问题 | P1；不自动执行文章中的命令 |
| 关联既有知识 | 只检索用户指定库/目录，提出候选链接，说明关联理由 | 双链建议和概念笔记 | P2；先解决路径、重名和错误链接 |
| 多文观点比较 | 用户给定若干来源；区分共识、冲突及证据 | 有来源映射的比较笔记 | P2；依赖多任务状态、去重和失败恢复 |
| 隔日主动回忆 | 用户主动发起复习，先回答后看反馈 | 复习记录、掌握程度与下一步 | P2；定时提醒由宿主承担并单独授权 |
| 文章更新追踪 | 用户再次提供同一来源时比较正文 | 变化摘要和新版本来源 | P3；保留用户编辑，不能直接覆盖成品 |
| 阅读记录可视化 | 经用户选择输出概念图或专题导航 | Canvas/Bases 或普通 Markdown 索引 | P3，可组合现有 Obsidian Skills |

### 建议的访谈协议

1. 保存前只问影响结果的配置，集中询问；已有偏好直接复用。
2. 用户选择“精读/访谈”后，再问目的与背景，避免每次剪藏都做长访谈。
3. 归档源文后，一次问一个问题，等待真实回答。允许跳过、结束或仅保存文章。
4. 清楚区分原文观点、Agent 解读、用户回答和推断；禁止补写用户没有说过的答案。
5. 用户结束后保存学习记录，与文章相互链接；明确记录未回答问题，恢复时从断点继续。

建议将原始阅读材料与个人思考分开：`note.md` 保持文章版本，`learning.md` 保存学习会话。后者是新增协议建议，当前 CLI 不会自动创建。可以先使用宿主文件工具验证需求，再决定是否增加 CLI 命令；不必立即接向量库或搭建第二个 Agent 平台。

### Harness 适配应明确能力合同

需要的能力是：发现/读取 Skill、执行 Node、读写选定路径、获取网页、可选浏览器、可选提问 UI。没有提问 UI 时可用普通对话；没有文件权限时不能声称已经写入 Obsidian；没有已登录浏览器时只能按已支持的回退流程处理。云端运行时必须说明如何访问 vault，不能假设它能写用户本机。

宿主负责交互、权限和模型，Skill 负责阅读流程，脚本负责抓取产物与验证，vault 保存用户知识。先提供 Codex 的可复现案例，再逐项验证其他宿主。宿主浏览器桥接要保留完整证据，不能降级成无来源的纯文本。

## 4. 知乎差异点如何验证

建议建立页面矩阵：单回答、专栏文章、长文、折叠正文、懒加载图、公式/表格/代码、已登录/未登录、验证码、付费限制、跳转与多回答干扰。使用用户有权读取的样本；公开仓库放合成 fixture、自己的样例或授权内容，不上传浏览器配置与他人全文。

同一批 URL、相近时间、相同可访问条件，分别测试本项目、官方 Clipper 和直接同类；记录宿主/浏览器/版本/日期，避免将登录态差异当成算法优势。

| 指标 | 计算或记录方式 |
| --- | --- |
| 正文覆盖 | 人工对照渲染页面的段落、标题、表格、代码块，记录缺失；不把字符数量等同语义完整 |
| 图片覆盖 | 应有正文图片与成功下载/保留远程/遗漏数量；分清是否排除头像广告 |
| 错误成品率 | 被限制或截断但仍当全文成功交付的次数 / 对应限制样本数 |
| 完成率 | 无人工修复即可得到可用笔记的次数 / 有权读取样本数 |
| 首次成本 | 安装步骤、耗时、付费调用、用户被询问次数 |
| 学习价值 | 阅读者是否找得到原文依据、能否复述并继续使用笔记；用访谈收集而非自行假设 |

发布测试结果时报告样本数与失败案例。当前仓库已有合成浏览器测试，不能将其描述为真实知乎成功率。知乎页面会变化，适配应有失败样例回归机制。

## 5. 名称、SEO 与 AI 发现

### 名称建议

**现阶段保留 `article-to-note`，加强副标题。** 推荐显示名称：`Article to Note — Obsidian Reading Skill for AI Agents`；中文：`面向 Obsidian 的网页阅读 Agent Skill`。

| 名称 | 优点 | 代价 | 建议 |
| --- | --- | --- | --- |
| article-to-note | 对应当前文章工作流，简短，已有使用习惯 | 不直接包含 Obsidian/Agent 语义 | 保留，用副标题、About 和示例补充 |
| web-to-note | 可覆盖更广网页 | 更泛，会引入任意网页转换预期 | 等实际范围扩大后再评估 |
| webpage-to-markdown | 转换意图明确 | 容易被理解为基础转换器，弱化学习 | 不建议作为主名 |
| obsidian-reading-skill | 目标群体明确 | 限制普通 Markdown 用户，后续改名也有成本 | 可作为定位描述 |

本轮查询显示 URL/web page to notes 已有 Taskade、NoteGPT、Thetawave 等相关结果；这只能说明存在替代与词义重叠，不能证明某个词搜索量更大、竞争更低或名称可注册。没有证据支持“改成 web page 就更容易搜到”。

### 必须分开的三层发现

1. **人找项目**：GitHub 仓库名、About、Topics、README、外部教程与引用。
2. **联网 AI 找项目**：能够被访问和索引的公开文本、清楚的能力边界、可引用的安装说明和案例。
3. **已安装 Agent 选 Skill**：本地 Skill 的 name/description 与触发例子。SEO 无法替代本地技能安装与发现。

OpenAI 的官方说明指出，模型先看到 Skill 元数据，再决定是否读取完整指令；description 应说明用户目标与触发条件。因此当前 description 缺少 Obsidian 和知乎语义，是值得验证的路由改进点。[Skills 官方说明](https://developers.openai.com/plugins/concepts/skills)。描述也不应无限堆词或包揽所有任务。[官方提示与技能建议](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)。

建议 description 草案（尚未修改 SKILL.md）：

```yaml
description: Save web articles, including supported Zhihu pages, as source-attributed Markdown notes for Obsidian or local folders. Use for clipping, full translation, bilingual reading, and optional study notes with local images.
```

修改后用“保存到 Obsidian”“知乎回答存笔记”“中英对照精读”“只查一个事实”等正反请求测试触发情况；新学习访谈真正实现后再增加相关触发描述。正文继续保留不适用范围。

### GitHub 上首先做什么

- About 建议：`Agent skill for web articles → Obsidian-ready Markdown: full translation, bilingual notes, local images, and a Zhihu browser adapter.`
- 推荐 Topics：`obsidian`、`agent-skills`、`codex`、`markdown`、`web-clipper`、`zhihu`、`translation`、`knowledge-management`。只加符合实际能力的宿主标签。GitHub 明确支持按 Topic 分类和检索。[官方说明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/classifying-your-repository-with-topics)。
- README 首屏说明目标用户、输入输出、独特处理和当前限制；附可复制请求及真实结果截图。
- 准备英文 README 与中文版本，互相链接；以自然语言覆盖 `web article to Obsidian`、`save Zhihu to Markdown`、`Codex reading skill` 等具体问题，不机械重复关键词。
- 发布可复现示例、版本记录与失败案例；贡献到匹配的社区目录前遵守对方规则，不做批量灌水。
- 获得真实使用反馈后决定是否上 Skill 分发目录或打包插件；先核验各分发方式的规则和安装步骤，不把未经验证的安装命令写进 README。

### 独立文档站与 AI 检索

如后续做 GitHub Pages 文档站，提供静态可读页面，使用准确 title/description、规范链接、sitemap 和内部导航，并通过自己的站点属性检查索引。GitHub 仓库页本身的 robots、页面头部和抓取规则不由我们完全控制。

Google 对 AI Overviews/AI Mode 的官方指导仍强调基本 SEO：页面可索引、有可展示摘要、正文可读、内部链接清晰、信息可靠，没有额外的技术准入要求。这个结论仅适用于其描述的 Google 功能，不应扩展成所有 AI 产品的统一排名规则。[Google 官方说明](https://developers.google.com/search/docs/appearance/ai-features)。

因此可选的 `llms.txt` 应当排在清楚的正文、案例和可抓取文档之后；本轮未取得它能提升项目在所有 AI 中排名的证据，也不能承诺提交目录后就会被推荐。不要混淆允许训练、允许搜索抓取和被推荐，它们并非同一件事。

### 如何判断优化有效

发布前记录一组目标查询；发布后在相同条件下定期记录 GitHub 搜索位置、文档站索引、来源流量、安装问题和首次成功笔记数量。对 AI 询问也保留产品、模型、日期、联网状态与回答来源，多次观察。没有基线数据时先谈“可发现性改善”，不宣称“命中率提高了多少”。

## 6. README 与发布路线

原 README 技术细节和安全边界比较完整，但首屏偏实现说明和版本修复，缺少目标用户、Obsidian 结果、产品演示和能力分层。本次已将定位、英文摘要、典型请求、输出目录、现有能力及进阶边界移到前面；保留原有安装、技术细节和限制。

后续按顺序补齐：

| 优先级 | 工作 | 完成标准 |
| --- | --- | --- |
| P0 开源准备 | 单独项目仓库、维护者选择许可证、发布内容检查 | 仓库仅包含项目与获准示例；有明确 LICENSE |
| P0 可信演示 | 一篇普通文章、一篇授权知乎文章，完整走通到 Obsidian | 有版本/日期/环境与图片检查结果，展示一次真实失败 |
| P0 首次使用 | Codex 安装与运行指南、依赖说明、问题反馈模板 | 新用户按文档完成第一篇，不依赖维护者解释 |
| P1 核心体验 | 可选精读访谈、learning.md、断点恢复 | 问题逐个进行，答案不编造，源文与个人理解可区分 |
| P1 Obsidian 输出 | 可选 Properties、文章标题文件名、稳定 ID 与 URL 去重 | 不破坏现有目录，不覆盖用户笔记；Properties 可被 Obsidian 识别 |
| P1 降低依赖 | 评估 Defuddle 等本地公开页提取 | 与现有样例比较质量与安装成本后再选择默认后端 |
| P2 可组合性 | 已有笔记检索、双链建议、多篇比较、任务恢复 | 有来源映射、断链检查、部分失败记录和幂等策略 |
| P3 扩展 | 版本差异、专题索引、可视化、宿主提醒 | 前述单篇闭环已被用户反复使用，再按反馈投入 |

不要因上传 GitHub 就自动移除 package.json 的 `private: true`：它限制 npm 发布，不阻止 GitHub 开源。Skill 的分发也不必先成为 npm 包。

### 当前工作区的发布注意点

本次 git status 显示 `article-to-note` 处于上层个人笔记仓库，项目目录本身显示为未跟踪。**应把项目文件单独导出到新的仓库目录再初始化或发布，不能直接推送当前上层仓库及其历史。** 排除 node_modules、个人配置、抓取文章、浏览器资料和密钥；保留 package-lock、脚本、测试和公开文档。当前未创建 GitHub 仓库或推送，也未替维护者选择许可证。

## 7. 最小验证路径

先完成一个可演示的任务：用户提供一篇可读取的技术文章 → 选择双语与本地配图 → Agent 询问阅读目的 → 生成可追溯笔记 → 逐个提出三个理解问题 → 保存用户回答与反馈 → 下次能从这篇笔记继续讨论。

该路径中的抓取与笔记已有基础，持久化学习会话是最值得优先验证的新部分。招募少量目标读者观察：是否完成首篇、是否愿意回答问题、是否再次打开笔记。用实际行为决定下一步投入，而不是先扩展更多平台。
